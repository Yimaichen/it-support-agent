# 员工 IT 支持调查助手

本项目帮助普通员工通过自然语言解决 IT 问题。系统会追问关键信息，查询公司资料，给出有依据的建议，并在需要人工处理时保存完整交接。当前前端使用 React，接口使用 FastAPI，对话由 Pi SDK 执行，业务数据保存在 SQLite。技术细节见[实现契约](SPEC.md)，架构、运行、评估和设计取舍均在本文说明。

## 一、项目目标

系统面向员工，而不是服务台坐席。员工通过 React 聊天界面描述症状、环境和业务影响，无需知道政策编号或支持团队。助手负责推进调查，覆盖账号锁定、区域服务异常、虚拟专用网络断连、数据访问申请和维护后故障。

可以直接处理的是有资料支持的只读调查和低风险指导，例如解释账号锁定流程、检查区域服务状态、按照知识库引导虚拟专用网络升级，以及说明权限申请路径。系统不会直接解锁账号、授予权限或重跑生产任务。涉及安全事件、审批尚未确认、生产变更、证据不足，或者员工明确要求人工时，应保存交接。

从员工视角看，理想成功是在几分钟内通过对话明确下一步并自行恢复，无需提交工单；需要人工时，也能在原对话中看到交接内容，不必重新描述问题。员工确认解决后，系统才结束问题并保存可复用经验。README 中的 6.0 秒中位数是单轮回复耗时，不是整个问题的解决时间。

## 二、为什么使用智能体

IT 调查的下一步取决于上一步证据。相同的“无法登录”可能来自账号锁定、区域事故、客户端版本或安全事件，固定问答难以覆盖这些分支。模型负责理解表达、选择工具、追问和解释；程序负责员工归属、数据权限、状态、去重和持久化。这个分工保留了语义灵活性，也让关键业务规则可以测试。

## 三、架构与层级分工

请求路径为“员工 → React 工作台 → FastAPI → `src/pi_agent.py` → `src/pi_runtime.py` → Node 中的 Pi SDK → 模型与业务工具”。React 负责对话、问题上下文和交接操作；FastAPI 负责接口、员工范围校验和事件流；Python 负责业务协调、十个工具和 SQLite；Pi 负责模型请求、工具循环、重试、压缩和私有会话；`data/` 提供公司合成资料。系统只有这一条模型执行路径。

## 四、调查流程与工具

每次提交使用稳定编号。业务层恢复员工、会话和当前问题，模型根据上下文选择追问或查询。八个查询工具覆盖知识库、服务状态、员工目录、政策、解决案例和本人历史；`manage_issue` 管理问题及材料关联，`save_handoff` 保存人工交接。模型可以连续调用工具，再基于真实结果回复。交接保留问题、影响、已查、已试、未知项和接手事项，员工随后可以继续同一问题。

## 五、资料、证据与记忆

`data/` 保存员工、设备、权限、服务状态、变更、政策、知识库和公共案例。服务状态用于判断是否有适用的公共事故，员工目录用于确认本人地区、设备和权限，知识库提供调查步骤，政策决定直接处理与人工审批的边界，公共案例只作为历史线索，个人历史只对本人开放。检索使用双语分词、别名和 BM25，来源编号、资料时间和适用范围随结果返回。Pi 文件保存模型对话，SQLite 保存消息、问题、证据、提交、工具、交接和成功经验。只有员工可信确认才能形成私有经验，问题重开后对应经验失效。

## 六、员工界面

React 工作台分为对话列表、消息区域和问题上下文。员工可以搜索历史、新建对话、查看来源、下载交接、确认解决或重开问题。右栏展示真实调查活动和人工摘要，手机端使用抽屉保留核心操作。页面刷新只读取已保存状态，建议项只填入草稿，确认解决使用独立可信操作，不调用模型。

## 七、安装与运行

项目需要 Python 3.12、Node.js 22.19 或更高版本、npm、uv，以及可访问 DeepSeek 接口的有效密钥。解压后进入项目目录，先安装依赖和构建前端，再复制 `.env.example` 为 `.env`，只在本地 `.env` 中填写 `DEEPSEEK_API_KEY`。Windows 可以手动复制文件，其余配置保留默认值即可。首次运行需要联网下载依赖，真实对话需要联网调用模型。

```bash
uv sync --locked
npm ci --prefix pi-runtime
npm ci --prefix frontend
npm run build --prefix frontend
cp .env.example .env  # 然后编辑 .env，填写 DEEPSEEK_API_KEY
uv run python scripts/run_logged.py
```

启动后访问 `http://127.0.0.1:8503`，日常启动只需最后一条命令。数据库和私有会话会在本机 `runtime/` 下自动创建，不需要另外安装 SQLite 或手动建表。提交包不包含任何已填写的密钥。

## 十、如果接入真实公司系统，需要怎么改

现在项目使用的是本地模拟数据。真正放到公司使用后，首先要解决四个很实际的问题：怎么确认员工身份，怎么避免看到不该看的内容，怎么查询真实系统，以及系统出错后怎么恢复。模型仍然负责理解问题和组织调查，但“你是谁、你能看什么、你是否真的操作成功”必须由公司系统给出答案。

### 10.1 先确认员工身份，不能随便切换成别人

员工通过公司的统一登录进入系统，不能在页面上随意选择另一个员工。登录状态由公司系统确认，后端据此决定当前用户是谁。员工换部门后，能看到的内容随之调整；员工离职后，账号、历史对话和系统访问权限都要及时关闭。涉及账号恢复或敏感数据时，还应再确认一次本人身份，避免别人拿着已登录的电脑冒用账号。

### 10.2 不同岗位看到不同内容，能看也不等于能改

普通员工只能看自己的记录，服务台人员只能处理分配给自己的问题，安全人员才能查看安全事件，数据负责人才能批准对应的数据权限。即使模型知道某份资料存在，也不能绕过这些限制去查询。搜索资料时就应先排除无权内容，而不是把内容交给模型后再提醒它保密。查看和修改也要分开，例如员工可以看到账号状态，不代表可以自行解锁管理员账号。

### 10.3 把本地模拟查询逐步换成真实查询

账号问题查询公司的账号系统，服务异常查询监控平台，公司规定查询正式知识库，人工处理查询服务台工单。每次查询都要说明数据来自哪里、什么时候更新，以及查询失败的原因，不能把旧数据当作当前状态。员工要求转人工时，系统应真正创建工单并返回工单号；发送失败可以重试，但重复点击不能生成多张相同工单。后续状态变化也要同步给员工。

### 10.4 出错时要能发现、能追查，也能恢复

一次员工请求应有统一编号，把页面提交、模型处理、工具查询和人工工单串起来。出现问题后，技术人员能看清卡在哪一步，而不是只看到“系统异常”。服务重启不能丢失问题和交接，重复请求不能造成重复操作。平时还要观察响应时间、查询失败、转人工、真正解决和问题重开等情况；上线新模型或新工具前先小范围试用，发现效果变差时能够退回旧版本。

## 十一、关键设计取舍

设计取舍围绕三个目标展开：调查路径要灵活，业务事实要确定，系统行为要能够复核。我没有把全部逻辑交给模型，也没有用大量固定分支模拟理解，而是把语义判断与程序控制放在各自适合的位置。

### 11.1 单模型调查，而不是多智能体编排

当前问题需要连续理解上下文，多个智能体会增加信息转述、状态同步和成本，也会模糊责任边界。单模型可以直接根据新证据调整调查，Python 则提供确定性的工具与状态约束。未来只有出现独立且可验证的任务，例如批量资料审核或离线质量评估，才值得引入独立智能体；不会为了增加架构复杂度而拆分运行时。

### 11.2 Python 与 Node 双运行时

Python 已承载检索、数据校验、权限和 SQLite，Pi SDK 则在 Node 中提供模型循环、工具协议、压缩和私有会话。保留两者可以避免重写已经验证的能力，代价是需要维护 JSON 桥接、两套依赖和进程生命周期。项目通过锁文件、类型检查、工具白名单、结构化事件和统一启动器控制这部分复杂度。

### 11.3 SQLite 与 Pi 文件分工

SQLite 是业务事实的权威来源，Pi 文件只负责模型继续对话所需的协议和记忆。这样即使模型上下文被压缩，问题、证据和交接仍然完整；即使页面重建，也不需要解析私有模型文件。代价是两个存储之间没有分布式事务，因此提交编号、工具调用编号、执行租约和中断记录必须共同防止重复执行与迟到写入。

### 11.4 BM25 检索，而不是立即引入向量库

当前语料规模较小，来源、版本和适用范围比语义相似度更重要。双语分词、别名和 BM25 足以提供可解释检索，也便于定位漏检原因。向量检索可以作为未来补充，但需要与关键词结果融合，并在检索后继续判断资料有效期和权限；检索分数不能直接升级为诊断置信度。

### 11.5 可信确认与完整回复发布

模型只能提出建议，员工可信操作才能改变解决状态，这使“助手说完成”和“员工确认恢复”成为两个不同事实。完整回复在脱敏后统一发布，减少未经处理内容的暴露，等待阶段用真实工具活动反馈进展。这个选择牺牲了逐字输出体验，因此生产版本还需要测量首字延迟，并评估经过安全处理的分段发布。

## 十二、后续可以沉淀和优化的能力

除了修复当前问题，还可以把这次项目中的对话、工具、日志和评估结果整理成长期可复用的能力。这样后续优化不只是反复调整提示词，而是逐步形成一套可以持续改进的系统。

### 12.1 沉淀持续的评测体系

把典型问题、多轮对话、预期工具、合格回复和交接结果整理成标准测试集。每次修改模型、提示词或工具后自动运行，对比正确率、解决率、响应时间和成本；固定题用于防止旧问题复发，新题用于检查真实泛化能力。

### 12.2 建立失败案例和知识改进闭环

将失败对话按资料缺失、检索错误、过度推断和交接不当等原因分类，再转成新的测试用例或资料修订任务。员工确认有效的解决经验，经审核后可以沉淀为公共案例，让后续调查逐渐受益，而不是每次从零开始。

### 12.3 优化模型、检索和成本的使用方式

简单查询和摘要可以使用更快的模型，复杂调查再使用能力更强的模型；同时评估缓存、检索排序和工具调用次数是否还有优化空间。每次调整都同时比较质量和成本，避免为了少量提升带来明显延迟。

### 12.4 把场景建设变成可复用的方法

将资料格式、调查步骤、工具接口、交接模板和测试用例整理成一套场景建设规范。以后增加新的 IT 问题时，可以按同一套方法补齐能力并快速验收，也更容易判断哪些部分可以复用到其他内部支持场景。
